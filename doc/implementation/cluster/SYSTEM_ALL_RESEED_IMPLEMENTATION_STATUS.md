# Implementation Status: Safe `--system=all` Reseed Without `--force`

Tracks delivery against `doc/implementation/cluster/SYSTEM_ALL_RESEED_FIX_PLAN.md`. Doc step 9 (adapting monolithic file-based mysqldump restore) remains out of scope, exactly as the design doc specifies.

## Delivered (steps 1-8)

**Live plugin-existence check.** `dbhelper.GetPluginStatusConn` (`utils/dbhelper/plugins.go`) is a connection-pinned `SHOW PLUGINS` lookup, resolving to `PluginAbsent` / `PluginActive` / `PluginNotInstalled` / `PluginPresentNotActive` / `PluginAmbiguous`, matched case-insensitively (plugin names are effectively case-insensitive in MariaDB/MySQL). It is the restore-time-truth counterpart to the monitoring cache `GetPlugins` feeds (`server.Plugins`), which can be stale or disabled.

`PluginNotInstalled` is a separate case from `PluginAbsent`: `SHOW PLUGINS` can list a *known* plugin (observed in production for `QUERY_RESPONSE_TIME`) as a present row with status `NOT INSTALLED`, not simply omit it from the result set the way a truly unrecognized plugin name would. Before this was split out, that row fell into the same default branch as a genuinely suspicious status (e.g. `DISABLED`), so a normal, replay-safe destination state aborted the whole reseed. `resolveInstallPluginSkip` (`cluster/srv_job_backup.go`) now treats `PluginAbsent` and `PluginNotInstalled` identically — both let `INSTALL PLUGIN` execute normally — mirroring the same `NOT INSTALLED` check `ServerMonitor.InstallPlugin` (`cluster/srv.go`) already used for the ordinary (non-reseed) install path.

`restoreSplitdumpFileGo` applies no blanket error-suppression for `mysql.system-all`. Instead, `execSplitdumpSingle` applies a narrow `INSTALL PLUGIN` skip guard (`resolveInstallPluginSkip`, live lookup via `GetPluginStatusConn`): only an unambiguous ACTIVE match is skipped; absent and NOT INSTALLED both execute normally; every other outcome (present-but-not-active, ambiguous, lookup error) surfaces as a normal error. The deliberate-skip log line is `LvlDbg`, not `LvlInfo` — an already-ACTIVE plugin is the common case on a repeatedly-reseeded or provisioned-then-reseeded destination, and logging it at INFO on every such statement floods normal restore logs. Every other statement class propagates errors unconditionally, including retry-exhaustion. Unit coverage: `TestGetPluginStatusConnNotInstalled(CaseInsensitive)` in `utils/dbhelper/plugins_test.go`; `TestResolveInstallPluginSkipNotInstalledExecutesNormally` / `TestExecSplitdumpSingleExecutesNotInstalledPlugin` in `cluster/srv_job_backup_system_reseed_test.go`.

**`CREATE USER` collision fallback.** A plain `CREATE USER` statement in `mysql.system-all` for an account that already exists on the destination (e.g. `mariadb.sys`@`localhost`, pre-created by `mariadb-install-db`/`mysql_install_db` on any non-empty instance, or any account independently bootstrapped on both sides) fails with `ER_CANNOT_USER` (1396) and previously aborted the whole reseed. `execSplitdumpSingle` (`isCreateUserStatement`, `isCannotUserError`) now catches exactly that error for exactly that statement shape and replays it as `ALTER USER` instead, so the account ends up matching the source's dumped definition rather than the reseed failing or the destination's stale definition being silently left in place. This is deliberately narrow: `CREATE USER IF NOT EXISTS` is excluded (a 1396 there has some other cause and must still propagate), and mysqldump's `--system=all` output emits one `CREATE USER` per account, so the fallback is not attempted against multi-account statements. If the `ALTER USER` fallback itself fails (for a reason other than the protected-system-account case below), the reported error carries *both* the original 1396 and the fallback's own error text, `errors.As`-reachable back to the original `*mysql.MySQLError` through the `%w` wrap — the bare "already exists" is not actionable once a fallback was attempted, so the fallback's failure reason (privilege issue, a version/flavor clause the rewrite doesn't handle, etc.) is not discarded. A transient (lock-wait/deadlock) failure specifically on the `ALTER USER` fallback statement is retried like every other statement class in this function, not treated as an immediate permanent failure — the retry loop only inspects the wrapped/original error by default, so `altErr`'s own retryability is checked explicitly rather than being invisible to it. Unquoted/backtick/quoted account specs are parsed via `parseCreateUserAccount`/`parseCreateUserToken`, including doubled-quote (`''`/`""`/` `` `) escaping; a parse failure is treated the same as "not a CREATE USER statement" rather than guessed at. Unit coverage: `cluster/srv_job_backup_system_reseed_test.go`. Live coverage: `regtest/test_direct_reseed_system_all.go`'s `TestDirectReseedSystemAllPreExistingUserAppliedViaAlterUser`.

**Protected system-account skip.** MySQL 8's `SYSTEM_USER`-protected bootstrap accounts (`mysql.sys`/`mysql.session`/`mysql.infoschema`, `mysql.system_user=1` in `mysql.user`) always pre-exist, so their `CREATE USER` always hits 1396 and triggers the `ALTER USER` fallback above — but that `ALTER USER` itself fails with `ER_SPECIFIC_ACCESS_DENIED_ERROR` (1227) unless the replay connection holds the `SYSTEM_USER` privilege, which repman's monitoring credential is not guaranteed to have. Since these accounts are created identically by the engine itself (not by prior backup content) on any instance of that server version, the destination's own copy is already correct, so `execSplitdumpSingle` treats exactly that combination — 1227 on the `ALTER USER` fallback, for an account matching `isKnownProtectedSystemAccount`'s allowlist — as a deliberate, `LvlDbg`-logged skip, not a fatal error. This is narrowly gated on the error code AND the **full account identity**, not the user name alone: MySQL/MariaDB account identity is `user@host`, and these four accounts are always created at `@localhost`, so the match requires host `localhost` (case-insensitive, matching host-name comparison semantics) and an exact, case-sensitive user-name match against `mysql.sys`/`mysql.session`/`mysql.infoschema`/`mariadb.sys` (case-sensitive because MySQL/MariaDB user-name comparison is case-sensitive by default, unlike host names) — an ordinary account that merely reuses one of these user names on a different host does not match. An access-denied failure on an ordinary account (e.g. a genuine `CREATE USER` privilege misconfiguration on the replay connection) still surfaces as a fatal error unchanged. Unit coverage: `TestExecSplitdumpSingleProtectedSystemAccountSkipped` / `TestExecSplitdumpSingleAccessDeniedOnOrdinaryAccountIsFatal` in `cluster/srv_job_backup_system_reseed_test.go`. Not covered by a regtest — reliably driving a replay connection that lacks `SYSTEM_USER` while otherwise having the privileges the rest of this suite depends on isn't practical in the current harness (same reasoning `TestExecSplitdumpSingleFatalOnNonActivePlugin`'s present-but-not-ACTIVE branch is unit-only, not regtested).

**Boundary classification.** `splitdump.ClassifyStream` (`utils/splitdump/classify.go`) splits one mariadb-dump/mysqldump stream into application SQL and system-catalogue SQL, reusing `isSystemSectionBoundary` and `isNonSystemSectionHeader` (`utils/splitdump/split.go`) — the same section-header rules `SplitDumpLineParser` already used, mechanically extracted so both share one definition. It streams line-by-line with a hard per-line ceiling (`classifyMaxLineSize`, 1GiB — MySQL/MariaDB's own `max_allowed_packet` protocol ceiling, so no legitimate line can exceed it), never accumulating the whole stream or section in memory.

Boundary contract: the system section is **not** a single EOF-bounded run. Any line matching `isSystemSectionBoundary` (`INSTALL PLUGIN`/`CREATE USER`) switches routing to the system-catalogue artifact; any line matching one of the dump's other recognized section headers (`USE`, table schema/data, view, routine, event, trigger) switches routing back to application SQL — and a later system-section-boundary line can switch it back again. This mirrors `SplitDumpLineParser`'s own proven dispatch, which opens `mysql.system-all` in append mode (the same mode as its routine/event/trigger sections) for exactly this reason: it is re-entrant. Confirmed by a real production case: `mariadb-dump --system=all`'s "stats" component dumps `mysql.innodb_table_stats`/`column_stats`/etc. as ordinary tables (`USE mysql;` then normal table-structure/data sections) after the `INSTALL PLUGIN`/`CREATE USER`/`GRANT` statements that open the system section, and `ClassifyStream` must route that reappearance back to application SQL, not treat it as a boundary violation.

**Shared replay helper.** `restoreSystemCatalog` (`cluster/srv_job_backup.go`) is the single, policy-free SQLx path that replays a `mysql.system-all` splitdump artifact over one pinned connection: FK/UNIQUE session state only (`prepareRestoreConn`), then a plain statement stream. It never calls `buildLogicalRestorePreamble`, `ResetMaster`, or applies GTID. It reports `progressed bool` — whether any statement actually committed before a failure — which both normal splitdump restore (`restoreSplitdumpWithMysql`'s dispatch, which routes `mysql.system-all` here) and direct-reseed retry orchestration use.

**Atomic artifact lifecycle** (`cluster/srv_job_reseed.go`). A direct reseed's extracted system-catalogue SQL is written to a temp directory, validated (gzip full-stream decompress, manifest, metadata), then published via `os.Rename` — so any reader only ever sees a complete artifact. Metadata tracks `Artifact_State`: `published` → `replay-in-progress` → `replay-succeeded` / `replay-failed` / `replay-failed-safe`. The two failure states are distinguished by `restoreSystemCatalog`'s `progressed` signal: `replay-failed-safe` means nothing committed (safe to redo from the beginning); `replay-failed` means at least one statement committed (not safe to redo — see narrow retry scope below). `isDirectReseedArtifactRetryableFromStart` is the single predicate gating this.

**Two-phase direct reseed.** `JobRejoinMysqldumpFromSource` (`cluster/srv_job_backup.go`) streams application SQL to the `mysql` client while routing system SQL to the artifact writer (phase one), then replays the published artifact through `restoreSystemCatalog` before any `StartSlaveChannel` call (phase two). Failures are stage-labeled (`application restore` / `system extraction` / `system catalogue replay` / `replication restart`) per the design doc's Cancellation and Failure Semantics table, including correct attribution when a classify failure's `cancel()` collaterally kills both subprocesses. Both the client-bound and artifact-bound writers feed the same `dest.reseedBytes` progress counter, so a long system-only tail doesn't look stalled to the watchdog.

**Internal retry.** `RetryDirectReseedSystemCatalog` (`cluster/srv_job_reseed.go`) is an internal-only entry point (no new API/CLI/GUI surface in v1): it validates artifact identity and structural integrity, enforces the narrow retry scope above, then invokes only `restoreSystemCatalog` — never `ResetMaster`, GTID application, or application-data replay — restarting replication only on success.

**Family/version compatibility.** Two checks, both built on `isDirectReseedArtifactVersionCompatible` (family and major.minor must match; patch-level drift is tolerated — the same rule `CheckLogicalBackupToolVersion`/`CheckPhysicalBackupToolVersion` in `cluster/cluster_bck.go` apply to backup/restore tool version drift):
- `CheckDirectReseedArtifactVersion(dest, extra)` compares the artifact's recorded destination family/major.minor (captured at publish time) against `dest`'s current version at retry time. Called by `RetryDirectReseedSystemCatalog` only when `cluster.Conf.BackupRestoreVersionStrict` is set — a retry is one-shot and admin-triggered, so a warning about something that proceeds regardless isn't actionable, and there's no periodic monitoring tick to ever clear a persisted warning state.
- `CheckDirectReseedSourceDestVersion(source, dest)` compares the source and destination servers directly, before `JobRejoinMysqldumpFromSource` starts any state-changing side effect. A source/destination version difference is not inherently unsafe — it is routine for logical (mysqldump-based) reseed (e.g. seeding a replica on a newer point release mid rolling-upgrade, or a cross-flavor migration), which is part of why logical reseed exists as an alternative to physical restore. This check is therefore opt-in, only evaluated and only blocking when `BackupRestoreVersionStrict` is set.

Both call sites log at `LvlErr` and return an error naming the flag before blocking; neither persists a `cluster.SetState` warning (unlike the periodic backup-tool-version checks — a one-shot retry/reseed action has no future tick to clear one, and reusing an existing WARN code would collide, since `SetState` keys are namespaced only by `code@serverURL`).

**Retention.** `PurgeExpiredDirectReseedSystemArtifacts` (`cluster/srv_job_reseed.go`) reuses the existing `backup-keep-last` config knob and never purges anything but confirmed-successful, superseded artifacts — a published-only, still-in-progress, or failed artifact is never touched. Wired into the cluster monitoring loop's hourly tick (`cluster.go`, `heartbeats%3600==0`, alongside `ResticPurgeRepo`). Because the knob is reused rather than dedicated, `backup-keep-last=0` ("keep forever") also opts this unrelated artifact class out of cleanup for an operator who set it for ordinary backup-retention reasons; a `LvlWarn` log fires per affected server (`hasDirectReseedArtifactDir` gates it to servers that actually have a published artifact, so clusters that have never used direct reseed stay quiet) so that isn't silent. Orphaned `.tmp-*` temp directories — left behind if the process dies (OOM-kill, SIGKILL, host reboot) mid-capture, since the only other remover, `discard()`, runs synchronously inside `JobRejoinMysqldumpFromSource` and never fires across a restart — are reaped by `reapOrphanedDirectReseedTmpDirs` in the same sweep regardless of `backup-keep-last`, gated on `server.IsReseeding` being unset (a writer this process still holds open always keeps that flag set for its whole lifetime, so an idle server can't own a `.tmp-*` dir found under its artifact root).

**Regtest scenarios** (`regtest/test_direct_reseed_system_all.go`, wired into `regtest/regtest.go` and `server/regtest.go`): empty destination, plugin-already-ACTIVE skip (using a live `GetPluginStatusConn` lookup and explicitly proving ACTIVE, not merely present), pre-existing-user `CREATE USER` collision resolved via the `ALTER USER` fallback above (`TestDirectReseedSystemAllPreExistingUserAppliedViaAlterUser`, verified by reading back `mysql.user.max_user_connections` on the destination and confirming it matches the source, not the destination's stale pre-reseed value), phase-two failure retains the artifact and is repaired and retried live via `RetryDirectReseedSystemCatalog`, and `backup-split-mysql-user` single-authority (no duplicate user replay). Both new/changed scenarios reset their probe user/table state with an explicit `DROP ... IF EXISTS` before each run rather than relying on `CREATE ... IF NOT EXISTS`/`IF NOT EXISTS` no-ops, so a rerun against a persistent (non-recreated) cluster starts from the same known state every time instead of silently inheriting whatever a prior run left behind. Both also explicitly tear down their own probe objects (user and/or table, on both master and destination) before reporting PASS, verified rather than trusted (a `mysql.user`/`information_schema.tables` read-back, not just checking the `DROP` itself returned no error) — `server/regtest.go` runs scenarios sequentially against one shared cluster outside SUITE mode, so leftover probe state or schema drift would otherwise leak into whichever scenario runs next. None of this has been run against live infrastructure in this environment yet — see the mandatory follow-up below.

The phase-two-failure/retry scenario (`TestDirectReseedSystemAllRetainsArtifactOnPhaseTwoFailure`) originally forced its deterministic failure with the same `CREATE USER` collision the fallback above now resolves — landing the fix made that mechanism unusable (the collision it relied on stopped being fatal), so the scenario was re-mechanized around a dangling column-level `GRANT` (drop a granted column on the source before dumping; `--system=all` still dumps the now-stale `mysql.columns_priv` row, and phase one recreates the probe table from its post-drop structure, so the column-level `GRANT` in phase two has nothing to attach to).

That re-mechanization has a structural consequence worth stating plainly: `--system=all` dumps every account, so the probe grantee's own `CREATE USER` necessarily appears in the artifact and necessarily precedes the `GRANT` that targets it (a dump tool can't validly emit a `GRANT` to an account it hasn't created yet) — and since the `CREATE USER` fallback above now makes that statement succeed (directly or via `ALTER USER`) instead of aborting, `progressed` is true by the time the `GRANT` fails, every time. The artifact therefore deterministically lands in `replay-failed`, not `replay-failed-safe`, and `RetryDirectReseedSystemCatalog` correctly refuses to redo it from the beginning. The scenario asserts that refusal as the expected outcome (still accepting a genuine safe-retry success too, in case the assumption above doesn't hold for some dump variant) rather than treating it as a test failure the way an earlier version of this scenario did — that earlier version's "if not-safely-retryable, fail the test" branch made it structurally unable to pass, since the only outcome it could actually reach was the one it treated as a failure. Proving the *other* valid outcome from this design doc's own scenario 4 (a genuine `progressed=false` retry succeeding from the beginning) would require the deliberate failure to be the very first statement in the whole artifact, which isn't constructible from plain SQL against a symmetric source/destination pair in this harness — that gap is tracked in the Mandatory follow-up below, not silently assumed away.

Accepting the refusal as expected surfaced two further, separate hygiene problems for this shared-cluster harness (`server/regtest.go` runs scenarios sequentially against one shared cluster outside SUITE mode, so anything a "passing" scenario leaves broken silently poisons every later scenario on that cluster):

- **Replication left stopped.** `RetryDirectReseedSystemCatalog` only restarts replication on its own success path (by design — replication must never resume on top of a refused retry), so a scenario that just logs the refusal and returns leaves the destination's slave threads stopped. The refusal branch now restarts every replication channel directly (`ServerMonitor.StartSlaveChannel`, mirroring the exact loop `JobRejoinMysqldumpFromSource`/`RetryDirectReseedSystemCatalog` run on their own success paths) and verifies `CheckSlavesRunning()` before returning.
- **Schema drift left on the destination.** `RetryDirectReseedSystemCatalog` replays only the frozen system-catalogue artifact, never phase-one's application/schema restore — so the scenario's own repair step (`ADD COLUMN probe_col`, applied to the destination only, purely to give the artifact's dangling grant a target the source no longer has) is never undone by anything else, in *either* PASS branch. Left alone, the destination keeps a column the source doesn't have. The function now explicitly reconciles both sides to a clean, identical state (drops the probe table and probe user on both master and destination) and verifies the table is actually gone via `information_schema.tables` before returning true, rather than trusting the drops alone or relying on some later scenario's own full reseed to incidentally overwrite the drifted table (mysqldump's `--add-drop-table` default would eventually do that for this specific table, but that's an incidental side effect of unrelated code, not something this scenario should depend on to call itself clean).

## Known follow-up: artifact-state crash safety (not implemented)

The artifact's `Artifact_State` metadata field is the safety gate `RetryDirectReseedSystemCatalog` trusts to decide whether a from-the-beginning retry is safe. Its durability today relies only on `os.Rename`/`os.WriteFile` returning successfully — there is no explicit `File.Sync()` before close, and no fsync of the containing directory after the rename that publishes an artifact or updates its state file. On most POSIX filesystems, a rename is not guaranteed durable against a crash until the containing directory is fsynced; a process/host crash at the wrong moment (after `setDirectReseedArtifactState` writes `replay-in-progress` but before that write is durable, immediately followed by a crash mid-replay) could in principle leave the on-disk state stale or ambiguous relative to what actually happened in the database.

This is scoped as a follow-up, not a blocker for the primary reseed-path fix: the acceptance bar for this delivery is correct reseed/retry *logic*, not full crash-consistency hardening of the metadata store. If artifact state is going to keep being trusted as a hard safety gate (which it is, by design), add explicit fsync-before-close on the artifact/metadata files and fsync of `direct-reseed-system/` (and its parent) after each publish/state-transition rename, verified with a fault-injection test before relying on it as a durability guarantee rather than a best-effort one.

(MySQL 8's `SYSTEM_USER`-protected accounts, the other risk this fallback originally carried, are now explicitly handled — see "Protected system-account skip" above, not this out-of-scope list.)

Pre-existing, unrelated to this delivery (belongs to doc step 9's monolithic-restore scope). Worth its own ticket.
